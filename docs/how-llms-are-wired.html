How LLMs are wired:
the input/output contract.

A mental model for engineers who think in APIs, request/response and contracts. The claim is simple: an LLM is blob in, blob out — a list of integers goes in, a probability distribution over the next integer comes out. Roles, memory, chat history, RAG, system prompts: all of it is convention layered on top by glue code.

Everything asserted here about prompt formats is shown, not just stated — the exhibits below are the real chat templates, fetched from each model's published tokenizer config, rendered on the same two messages.

01Two layers, not one

Most confusion comes from collapsing two distinct layers into one idea of "the model". They are stacked, and only the top one looks like software you have written before.

LayerWhat it isNearest thing you already know
The API surface POST a JSON body with model, messages, temperature, max_tokens. JSON or a stream comes back. An ordinary REST endpoint. Rigid, versioned, deterministic in shape — the same request always parses the same way.
The raw model contract A flat sequence of token IDs in; a probability distribution over the next token out. One vector in, one vector out. That is the entire native interface. A pure function. No routes, no fields, no types — just f(int[]) → float[vocab].

Everything in between — turning your messages array into one flat list of integers — is glue code. Hosted providers hide it. Run a model yourself and you inherit it. 

Your JSON  ──►  [ glue: tokenize + apply chat template ]  ──►  [1023, 88, 5501, ...]  ──►  MODEL
                                                                                          │
Your app   ◄──  [ glue: detokenize + wrap in JSON ]  ◄──  probability distribution  ◄────────┘

02The blob is the whole conversation

Two consequences fall out of "blob in, blob out", and both matter in production.

It is not just your latest message. The glue flattens the entire interaction — system prompt, every prior turn, your new message — into one long token sequence, consumed in a single forward pass.

The model is stateless. There is no memory between calls. Every request re-sends the full history. The continuity you feel in a chat is maintained entirely on your side by resending context. The model wakes up, reads the whole blob, answers, and forgets.

The comparison

This is a stateless web tier, exactly. The model is the request handler that holds nothing between calls; your conversation store is the session backend. "Memory" in an agent is your component to build — the model offers no persistence whatsoever. You decide what to keep, summarise or drop, and you re-inject it every single turn.

03Two buckets: knobs and data

What you send splits cleanly in two, and the split is not where people expect.

Bucket 1 — control parametersBucket 2 — the data blob
Contains temperature, top_p, max_tokens, stop, reasoning effort System prompt, task, chat history, RAG chunks, injected memory
Reaches the model? No. These sit outside the token sequence and configure the sampler — the code that picks a token from the output distribution. Yes. All of it is tokenised into the one flat sequence the model consumes.
Like Query hints or connection settings — they tune execution, not meaning. The request body.

The critical part: the model does not distinguish between the categories inside bucket 2. "Short-term memory", "long-term memory", "context", "history", "retrieved documents" are human-side organising concepts. To the model it is one undifferentiated stream of integers.

04So how does it tell a system prompt from user text?

Only through learned formatting cues — special delimiter tokens. The glue wraps each section in markers the model was trained to recognise. These are just more integers. During alignment the model saw millions of examples formatted exactly this way, so it learned, statistically, that text after the system marker tends to be authoritative and that it should speak as the assistant.

There is no parser

No schema, no config, no validator enforces these roles anywhere. It is convention baked in as a statistical habit. Which means the distinctions we care about are an illusion maintained by formatting — and that claim is testable. Below is what actually happens.

05What those exhibits actually prove

They go further than "the delimiters differ". Read them side by side and three things fall out that no amount of prose would convince you of.

Finding 1 · roles are learned, not built in

distilgpt2 has no chat template at all. The field simply does not exist in its tokenizer config. It is a pretrained base model that never went through alignment, so it has no concept of "system" or "user" — it can only continue text. Roles are not part of the transformer architecture; they are taught in post-training, and a model that skipped that stage does not have them.

Finding 2 · a role you send may not survive the trip

Mistral has no system role. Its template folds your system text into the front of the first user turn — the output is [INST] You are terse.\n\nName three primary colors.[/INST] with no separate system section at all. gpt-oss goes further and renames it: your system message is re-labelled developer, while the model's own synthesised system block — identity, knowledge cutoff, today's date, reasoning effort, channel rules — is inserted above it. You did not write any of that.

Finding 3 · the glue adds things you never sent

Nemotron injects <AVAILABLE_TOOLS>[] into the system section even though the request declared no tools. Between your clean messages array and the integers the tensor eats, a template you did not write is making decisions.

So "you code once against a common contract and each provider handles the last mile" is true at the surface, and the last mile is doing more than translation. The format is deterministic and rigid; the model's output is what is nondeterministic. Do not conflate the two.

06Why prompt injection works

This follows directly. If roles were enforced structure, pasting "ignore previous instructions" into a document could never work. But it is all one blob, and the model is only guessing from learned patterns, so hostile text inside a RAG chunk or a tool result can impersonate the system voice. Nothing protects the system instructions from retrieved content.

The comparison — and where it breaks down

This is the same shape of bug as SQL injection or XSS: untrusted input reaching an interpreter that cannot tell data from instructions. The difference is that those have a real fix. Prepared statements work because the database parses the query and the parameters separately — the structure is decided before the data arrives.

There is no prepared statement for a prompt. The exhibits above are the reason: the "structure" is delimiter tokens in the same stream as the data, recognised by a statistical habit rather than a parser. Escaping helps at the margins and guarantees nothing.

So treat every injected string — RAG chunks, memory, tool output, anything a user can influence — as untrusted input, and put the guarantees you need outside the model. Validate the output rather than trusting the instructions held.

07Where roles get taught

A model is built in three broad stages, and it is worth knowing which one produces the behaviour you rely on every day.

StageWhat happensWhat the model knows after
1 · Pretraining Corpus collection and filtering; tokenizer trained (the integer alphabet is frozen here); architecture chosen; next-token prediction over trillions of tokens. Grammar, facts, reasoning primitives. Nothing about system, user or chat. It is a text-completion engine — exactly the distilgpt2 exhibit.
2 · Post-training Supervised fine-tuning on instruction/response pairs formatted with the delimiter tokens; preference data; reward model; RLHF/DPO; safety tuning; tool-call formats. This is where roles are learned. SFT teaches the template; RLHF reinforces obeying the system voice over the user voice.
3 · Packaging Evaluation, optional quantisation, then weights + tokenizer + chat template wrapped in a serving stack (vLLM, TGI, Ollama) exposing an OpenAI-shaped endpoint. Unchanged — this stage only adds the glue that converts your JSON into that exact raw sequence.

That is precisely why the hierarchy is soft: it is a trained habit, not a parser. And why formats are family-specific: each lab picked its own delimiters at the fine-tuning step, which is exactly what the exhibits show.

08Running one yourself

Internal or frontier, the physics are identical — token IDs in, distribution out. Only the maintainer of the glue changes. Self-host and you own two pieces the providers hide:

  1. The tokenizer. Must be the exact one used at training time. It is the frozen alphabet; get it wrong and everything downstream is garbage.
  2. The chat template. Replicate the delimiters the model was tuned with, or it gets confused about who is speaking. Feed one family's format to another and output degrades, because those markers were never learned.

Serving tools — vLLM, Ollama, Hugging Face TGI — play the provider's role for you: hand them weights plus tokenizer config plus chat template, and they expose the familiar endpoint.

Checklist · using an LLM with no framework
  1. Match tokenizer and template to the model. Automatic on hosted APIs; silent-failure-prone locally.
  2. Own the statelessness. Re-send the relevant history every call.
  3. Budget the context window. Track token counts; decide what to keep, summarise or drop.
  4. Write a tight system prompt. Durable rules, role, constraints, output contract — the strongest steering lever.
  5. Keep the task payload in the user turn, separate from instructions.
  6. Use few-shot for format control. Not a feature or a flag — just worked examples pasted into the blob before your real question. Showing the shape beats describing it.
  7. Set the sampling knobs deliberately. Low temperature for extraction, higher for generation; set max_tokens and stop.
  8. Force structured output when code consumes it, and use schema/JSON mode where offered.
  9. Validate and guard the output. It is the only nondeterministic surface in the pipeline.
  10. Treat injected content as untrusted — see section 06.
  11. Handle timeouts, rate limits and partial streams yourself. No framework is catching them.

09The through-line

Summary

Input side: deterministic, rigid, and yours to control.

The build pipeline: taught the model to recognise the structure you send — as a habit, not a schema.

Output side: the single nondeterministic surface. Guard it.

The word "chat", the notion of "roles", the taxonomy of "memories" — convention wrapped around a stateless, blob-in/blob-out next-token predictor. Every guarantee you need beyond "the next token is probable" has to be built around the model, not expected from inside it.
